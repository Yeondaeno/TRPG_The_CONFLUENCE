# 03. P2P 동기화 — GM 허브 스타 토폴로지

**선행 조건**: 명세 01 완료 (`net.js` / `ui-net.js` 껍데기와 호출 지점이 존재해야 함)
**소유 파일**: `web/src/net.js`, `web/src/ui-net.js`, `web/vendor/**`
**설계 근거**: [ADR-001](../adr/001-p2p-sync.md) — 먼저 읽으세요

> `app.js` · `ui.js` · `store.js` · `rules.js`는 **수정하지 마세요.** 명세 02가 동시에
> 진행 중일 수 있습니다. 수정이 꼭 필요하다면 멈추고 이유를 보고하세요.

---

## 지켜야 할 단 하나의 원칙

> **P2P는 동기화 계층이지 저장 계층이 아니다.
> 네트워크가 하나도 안 붙어도 도구는 100% 동작해야 한다.**

3시간짜리 원샷을 시작하고 5분 만에 NAT을 디버깅하고 있으면 그날 세션은 망합니다.
**연결 실패는 정상 경로입니다.** 오류 팝업으로 세션을 막지 마세요.
연결이 안 되면 조용히 로컬 모드로 남고, 상태만 표시하고, 게임은 계속 굴러가야 합니다.

이 원칙을 어기는 구현은 완료로 치지 않습니다.

---

## 1. 토폴로지

```
        플레이어 A ─┐
        플레이어 B ─┼──▶ [ GM 단말 ] ◀── 진실의 원천
        플레이어 C ─┘         │
                              └─▶ Store (localStorage)
```

**GM 단말이 유일한 권위입니다.** 플레이어는 의도를 보내고, GM이 적용하고, 결과를 방송합니다.

풀 메시(9명 = 36연결 + 상태 합의)를 쓰지 않는 이유는 ADR-001에 있습니다.
요약하면: **TRPG에는 원래 심판이 한 명 있고, 그게 이미 답입니다.**

이 구조 덕에 [roadmap 2-2](../roadmap.md#2-2-방-상태-갱신에-경쟁-상태가-있다)의
경쟁 상태가 **구조적으로 사라집니다.** 락도 CAS도 필요 없습니다.

## 2. 라이브러리와 시그널링

- **PeerJS**를 씁니다. `web/vendor/peerjs.min.js`로 **벤더링**하고 빌드 시 인라인하세요.
  CDN을 쓰지 마세요 — 배포물은 외부 요청 0개인 단일 파일이어야 합니다(명세 01).
- **방 코드가 곧 피어 ID입니다.** 이게 PeerJS를 고른 이유입니다 —
  기존 "방 코드 입력" UX가 **한 글자도 바뀌지 않습니다.**
  - GM: `new Peer('hapgyeong-' + roomCode)`
  - 플레이어: `peer.connect('hapgyeong-' + roomCode)`
- **네임스페이스 접두사 `hapgyeong-` 필수.** 공개 브로커는 전역 ID 공간입니다.
- 4자 코드는 충돌할 수 있습니다. `host()`가 ID 선점 실패로 떨어지면
  "이미 쓰이는 코드입니다 — 새 코드를 생성하세요"로 안내하세요.
- STUN은 PeerJS 기본값으로 충분합니다. **TURN은 설정하지 마세요** — 유료이고,
  없다고 해서 이 도구가 못 쓰이는 게 아닙니다(로컬 폴백이 있으니까).

## 3. 프로토콜

모든 메시지는 `{ t: <타입>, ... }`. **버전 필드 `v: 1`을 넣으세요** —
세션 도중 누가 옛 파일을 열고 들어오는 일이 실제로 생깁니다. 버전이 다르면
접속을 거절하고 "파일 버전이 다릅니다"라고 알리세요.

### 플레이어 → GM (의도)

| 타입 | 내용 | GM의 처리 |
|---|---|---|
| `hello` | `{name}` | 접속 등록, 현재 상태 전송 |
| `claim` | `{char}` | **선착순 판정.** 이미 점유면 거절 응답 |
| `release` | `{char}` | 점유 해제 |
| `update` | `{char, patch}` | 점유자 본인인지 확인 후 적용 |
| `roll` | `{roll}` | 로그에 추가 후 방송 |
| `log` | `{text}` | 로그에 추가 후 방송 |

### GM → 플레이어 (방송)

| 타입 | 내용 |
|---|---|
| `state` | 전체 상태 (접속 직후 1회) |
| `patch` | `{path, value}` 델타 |
| `roll` | 굴림 결과 (전원에게 즉시) |
| `reject` | `{reason}` — 점유 거절 등 |
| `bye` | GM 종료 예고 |

### 검증은 GM이 합니다

플레이어가 보낸 `update`를 그대로 믿지 마세요.
- 그 캐릭터를 실제로 점유한 사람인지 확인
- HP는 `0..maxHp`, 잔향은 `0..100`으로 클램프
- 모르는 필드는 무시

악의를 막으려는 게 아니라 **옛 버전 클라이언트와 버그로부터 세션을 지키기 위해서**입니다.

## 4. 비밀 전송 — 이 명세의 숨은 목표

명세 01은 비밀을 **렌더링 단계에서** 가렸습니다. 임시방편입니다.
개발자 도구를 열면 데이터는 거기 있습니다.

P2P에서는 **근본 해결이 가능합니다.**

- GM이 `state`/`patch`를 보낼 때 각 수신자별로 **비밀 필드를 걸러서** 보냅니다
- 받는 사람이 그 캐릭터의 점유자면 포함, 아니면 필드 자체를 제거
- GM 본인은 전부 봅니다

즉 **다른 사람의 비밀은 애초에 그 브라우저에 도착하지 않습니다.**
사전 제작 캐릭터의 비밀은 세션 중반에 터뜨리도록 설계된 장치입니다
(준이 스승을 두고 도망친 일, 레오가 릴리스의 가문을 몰락시킨 사냥에 가담한 일).
미리 읽히면 그 장면이 죽습니다.

명세 01이 남긴 "임시방편" 주석을 이 구현으로 갱신하세요.

## 5. 폴백 사다리

이 순서대로 강등하고, **각 단계에서 게임은 계속 굴러가야 합니다.**

```
1. 로컬 우선   Store(localStorage)가 각자의 진실.
              연결 0명이어도 캐릭터시트·주사위·판정 전부 동작.
2. P2P 연결    붙으면 동기화가 얹힌다.
3. 연결 실패   조용히 1로 남는다. 오류로 막지 않는다.
4. 최후 수단   상태 JSON 내보내기 / 가져오기.
```

**4번을 반드시 구현하세요.** 이건 3번의 보험이 아니라 **GM 이탈의 해법**입니다.
스타 토폴로지의 가장 큰 약점이 "허브가 죽으면 끝"인데,
GM이 상태를 내보내 다른 사람에게 넘기면 그 사람이 새 허브가 됩니다.
파일 하나 주고받는 게 3시간 세션을 살립니다.

## 6. `ui-net.js` — 연결 상태 표시

**연결 상태가 항상 보여야 합니다.** 안 보이면 "내 HP가 왜 안 넘어가지?"를
디버깅하느라 세션이 멈춥니다.

- 상단바에 상태 배지: `로컬 전용` / `연결 중…` / `GM 허브 (7명 접속)` / `연결됨` / `연결 끊김`
- GM 화면에는 접속자 목록과 각자 점유한 캐릭터
- 연결이 끊기면 **자동 재접속을 시도**하되, 시도 중에도 로컬 조작은 계속 되게 하세요.
  끊긴 동안의 변경은 재접속 시 GM에게 다시 보냅니다.
- 접속 화면에 "GM으로 방 열기" / "방 코드로 참가" 두 갈래를 명확히 하세요.
  현재는 GM 지정이 입장 후에 이뤄지는데(`index.html:736-745`),
  허브를 세우려면 입장 시점에 정해져야 합니다.

## 7. 테스트

브라우저 두 개(또는 Playwright 컨텍스트 두 개)를 띄워 확인하고, 검사를
`tools/verify-ui.mjs`에 덧붙이세요. 브라우저 바이너리는 `/opt/pw-browsers`에
선설치되어 있으니 **`npx playwright install`은 실행하지 마세요.**

주의: 브라우저 컨텍스트가 다르면 localStorage도 분리됩니다. 같은 방을 공유하는
검사는 그 점을 감안해 설계하세요.

같은 머신의 두 탭은 STUN 없이도 붙으므로 **프로토콜 검증에는 충분하지만
NAT 통과를 검증하지는 못합니다.** 그 한계를 보고서에 명시하세요.
실제 NAT 통과는 서로 다른 네트워크의 사람 둘이 있어야 확인됩니다 —
**확인 못 한 것을 확인했다고 쓰지 마세요.**
