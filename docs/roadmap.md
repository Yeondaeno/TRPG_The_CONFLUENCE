# 개선점과 구현 방향

원본 자료 3종(룰북 · 기성캐릭터 · 웹도구)을 읽고 정리한 분석입니다.
데이터 수치 문제는 [`errata.md`](errata.md)에, 여기에는 **도구·구조 문제와 만들 순서**를 적습니다.

## 먼저, 지금 좋은 것

깎아내리기 전에 — 이 자료는 원샷 TRPG로서 완성도가 상당히 높습니다.

- **1.4 결과의 4단계**가 진짜 설계의 중심입니다. "규칙에 없는 행동을 5초 안에 판정한다"는
  절차를 명문화했고, "실패해도 이야기가 멈추면 안 된다"까지 원칙으로 못 박았습니다.
- **1.5 그룹 판정**은 8인 파티라는 제약을 정면으로 다룬 몇 안 되는 장치입니다.
- **위상잔향**이 "탐험 압박 → 자원 소모 → 캐릭터 변화"를 한 축으로 묶습니다.
  단순 HP 소모전이 아니라 원샷 안에서 캐릭터가 변하는 근거가 됩니다.
- 사전 제작 16명이 **전원 관계선으로 짝지어져** 있습니다. 초면인 플레이어 9명이
  30초 만에 롤플레이를 시작할 수 있는 가장 실용적인 장치입니다.

아래 지적은 전부 "이 좋은 규칙이 도구에서 구현되지 않았다"는 이야기입니다.

## 1. 가장 큰 문제: 도구가 룰북의 핵심을 구현하지 않는다

웹도구는 잘 만들어진 **캐릭터시트 뷰어 + 주사위 굴림기**입니다. 하지만 이 시스템을
다른 d20 게임과 구별해주는 규칙들이 전부 빠져 있습니다.

| 룰북 규칙 | 웹도구 구현 | 그래서 세션에서 무슨 일이 나는가 |
|---|---|---|
| **1.4 결과의 4단계** (간판 규칙) | ❌ 없음. DC 입력란조차 없다 | 주사위 탭은 `2d8 [5,3] +2 = 10`만 출력. DC 비교·부분 성공 판정은 GM이 매번 암산 |
| 자연 20 / 자연 1 | ❌ 없음 | 대성공·실패의 특별 처리를 놓친다. `2d6`을 굴려도 자연 20 판정이 안 됨 |
| **1.5 그룹 판정** | ❌ 없음 | 8인 파티 전용 규칙인데, 8명이 각자 굴린 결과를 GM이 손으로 세야 함 |
| 3.1 잔향 임계치 페널티 | ⚠️ 숫자만 저장 | 잔향 60인 캐릭터에게 -2가 붙는다는 걸 아무도 안 알려줌 |
| 3.2 여파화 표 (d10) | ❌ 없음 | 시스템의 클라이맥스 장치가 종이 표로만 존재 |
| 2.3 부상 단계 | ⚠️ 수동 드롭다운 | HP 7/22인데 상태가 '경상'으로 남아있어도 아무 경고 없음 |
| 4.2 즉석 조합 | ❌ 없음 | 결정편 숫자만 있고 소모·제작 흐름이 없음 |
| 부록 A 캐릭터 제작 | ❌ 없음 | 17번째 플레이어가 오면 종이로 만들어야 함 |

**우선순위 1번은 여기입니다.** 동기화 버그보다 이게 먼저입니다 —
동기화가 완벽해도 GM이 여전히 암산을 하고 있으면 도구를 만든 의미가 절반입니다.

### 판정 엔진의 모양

지금의 "주사위 굴림기"를 "판정기"로 바꾸는 게 핵심입니다.

```
[캐릭터: 라비 ▾] [기술: 은신 (숙련) ▾]  vs  DC [12]  [상황 보정: -2 ▾]
                                                      → [판정]

  d20 [9] + AGI(+3) + 숙련(+2) + 잔향(-1) = 13   ≥ DC 12
  ─────────────────────────────────────────────
  성공 — 의도한 대로 이루어짐
```

여기서 중요한 건 **잔향 -1이 자동으로 들어갔다는 것**입니다. 캐릭터 상태를 이미
저장하고 있으니, 보정치를 사람이 입력하게 둘 이유가 없습니다. 현재 도구는
"수정치" 칸 하나에 전부 손으로 넣게 되어 있습니다.

그리고 결과 4단계는 `data/rules.json`의 `outcomeTiers`를 그대로 평가하면 됩니다:

```js
function resolve(natural, total, dc) {
  if (natural === 20 || total >= dc + 10) return 'crit';
  if (total >= dc)                        return 'success';
  if (natural === 1)                      return 'fail';   // 자연 1은 부분 성공보다 우선
  if (total >= dc - 4)                    return 'partial';
  return 'fail';
}
```

> 규칙서에 모호한 지점이 하나 있습니다: **자연 1이면서 DC-1인 경우** — 1.4 표는
> "자연 1 → 실패"와 "DC-1~DC-4 → 부분 성공"을 동시에 만족시킵니다. 위 코드는 자연 1을
> 우선했습니다. 반대로 정하고 싶다면 `rules.json`의 `outcomeTiers` 순서만 바꾸면 됩니다.

### 그룹 판정 화면

8인 파티가 이 시스템의 전제인데 도구에 흔적이 없습니다. 필요한 건 단순합니다 —
GM이 "전원 DC 12 생존술" 하고 선언하면 방 전체에 판정 요청이 뜨고, 각자 굴린 결과가
한 화면에 모여 과반 여부를 자동 집계하는 것. 조력자 +2도 여기서 처리됩니다.
**이게 이 도구가 종이 대비 가장 크게 이기는 지점입니다.**

## 2. 웹도구의 기술적 문제

심각도 순입니다. 재현 방법과 위치를 함께 적었습니다.

### 2-1. 아티팩트 밖에서는 저장 자체가 안 된다

**심각도: 치명**

`web/index.html:502` / `:508`

```js
const r = await window.storage.get("room_"+ROOM_CODE, true);
await window.storage.set("room_"+ROOM_CODE, JSON.stringify(state), true);
```

`window.storage`는 Claude 아티팩트 런타임 API입니다. 파일을 다운로드해 열면
이 객체가 없어서 `try/catch`가 삼키고 → `loadRoom()`이 매번 `defaultRoom()`을 반환합니다.
**동기화만 안 되는 게 아니라, 새로고침하면 내 캐릭터 HP까지 전부 초기화됩니다.**
접속 화면 안내문은 "나 혼자 보는 로컬 모드로 동작"이라고 적혀 있지만, 실제로는
로컬 저장도 되지 않습니다.

→ **즉시 고칠 것**: `localStorage` 폴백. 스토리지 계층을 인터페이스로 한 번 감싸면
`window.storage` → `localStorage` → 메모리 순으로 떨어지게 만들 수 있고,
현재 어느 모드인지 UI에 표시할 수 있습니다.

### 2-2. 방 상태 갱신에 경쟁 상태가 있다

**심각도: 치명**

`web/index.html:513`

```js
async function withRoom(mutator){
  ROOM = await loadRoom();   // ① 읽고
  mutator(ROOM);             // ② 고치고
  await saveRoom(ROOM);      // ③ 통째로 덮어쓴다
}
```

방 전체(캐릭터 16명 + 로그 300줄 + 선제권)를 하나의 키에 통으로 저장하면서
읽기-수정-쓰기를 원자적으로 하지 않습니다. 9명이 동시에 쓰는 상황에서 **마지막 쓰기가 이깁니다.**

재현: 전투 중 두 플레이어가 거의 동시에 주사위를 굴리면 → 둘 다 ①에서 같은 상태를 읽고
각자 자기 로그 한 줄만 추가한 뒤 ③에서 덮어씀 → **한 명의 굴림 기록이 사라집니다.**
HP 입력도 마찬가지로 되돌아갑니다. 4초 폴링(`:556`)이 덮어쓴 값을 다시 받아오기 때문에
플레이어 입장에서는 "입력한 HP가 잠시 후 원래대로 돌아가는" 증상으로 보입니다.

→ **해법은 락이나 CAS가 아니라 키 분리입니다.** 지금 한 덩어리인 상태를 쓰는 주체별로 쪼개면
경쟁 자체가 사라집니다:

| 키 | 쓰는 사람 | 충돌 가능성 |
|---|---|---|
| `room:{code}:char:{이름}` | 그 캐릭터를 점유한 플레이어 1명 | 없음 |
| `room:{code}:log:{순번}` | 추가만 하고 수정하지 않음 (append-only) | 없음 |
| `room:{code}:combat` | GM 1명 | 없음 |
| `room:{code}:claims` | 여러 명 — 여기만 CAS 필요 | 점유할 때만 |

부수 효과로 전송량도 줍니다. 지금은 주사위 한 번 굴릴 때마다 방 전체를 직렬화해서
올립니다(로그 300줄 포함). 분리하면 로그 한 줄만 올라갑니다.

### 2-3. 사용자 입력이 그대로 innerHTML에 들어간다

**심각도: 치명**

`web/index.html:525` (`el()`), `:668` (메모), `:849` (로그)

```js
list.appendChild(el(`<div class="log-item ${it.type}"><span class="t">${it.time}</span>${it.text}</div>`));
```

`it.text`는 `${PLAYER_NAME}: ${사용자입력}`입니다. 이름 칸이나 로그 입력에
`<img src=x onerror=alert(1)>`를 넣으면 **같은 방의 전원 브라우저에서 실행됩니다.**
캐릭터 메모(`:668`)도 `<textarea>` 안에 보간되므로 `</textarea>`로 탈출할 수 있습니다.

지인끼리 하는 세션이라 악의적 공격은 걱정 안 해도 되지만, `<`가 들어간 메모를 적으면
화면이 깨지는 건 실제로 일어납니다. 판정 이름에 `HP < 10일 때` 같은 걸 적으면 됩니다.

→ 문자열 보간 대신 `textContent`를 쓰거나, 최소한 이스케이프 함수 하나를 태웁니다.

### 2-4. GM 전용 비밀이 전원에게 보인다

**심각도: 주의**

`web/index.html:666`

```html
<div class="kv"><b>비밀 (GM 전용, 본인 플레이어에게만 살짝 알려주세요)</b> ${p.secret}</div>
```

캐릭터 카드를 클릭하면 **누구나** 그 캐릭터의 비밀을 볼 수 있습니다. 안내 문구로
"보지 마세요"라고 부탁하고 있을 뿐입니다. 사전 제작 캐릭터의 비밀은
"준은 그날 스승을 두고 도망쳤다", "레오는 릴리스의 가문을 몰락시킨 사냥에 가담했다"처럼
**세션 중반에 터뜨리도록 설계된 것들**입니다. 미리 읽히면 그 장면이 죽습니다.

→ 비밀은 `점유자 본인 + GM`에게만 렌더링. 데이터 자체를 안 보내는 게 이상적이지만,
공유 스토리지 구조상 어렵다면 최소한 렌더링 단계에서 가립니다.

### 2-5. 같은 캐릭터를 두 명이 점유할 수 있다

**심각도: 주의**

`web/index.html:595`. 점유는 2-2의 읽기-수정-쓰기를 그대로 타므로, 9명이 동시에
캐릭터를 고르는 **세션 시작 직후 1분**에 가장 터지기 쉽습니다.

### 2-6. 입력 중에는 동기화가 멈춘다

**심각도: 경미**

`web/index.html:555-559`

```js
const typing = ae && (ae.tagName === 'INPUT' || ...);
if (typing) return;
```

폴링이 4초마다 화면을 통째로 다시 그리기 때문에, 입력 중 커서가 날아가는 걸 막으려고
넣은 가드입니다. 하지만 결과적으로 **메모를 길게 쓰는 동안 그 사람만 남의 주사위 결과를
못 봅니다.** 전투 중에 이러면 꽤 답답합니다.

→ 근본 해결은 전체 재렌더를 그만두는 것입니다. 상태를 키로 쪼개면(2-2) 바뀐 부분만
갱신할 수 있고, 그러면 이 가드 자체가 필요 없어집니다.

### 2-7. 그 외

- **`lastRoll`이 로컬 변수** (`:687`) — 내 굴림 결과는 큰 글씨로 보이지만
  남의 굴림은 로그 탭에 한 줄로만 뜹니다. 전투 중 "방금 몇 나왔어?"가 반복됩니다.
- **타이머가 GM 화면에만 있음** (`:838`) — 원샷 페이스 조절이 목적이라면
  플레이어에게도 보여야 압박이 됩니다.
- **몬스터 4종이 하드코딩** (`:443`) — 시나리오가 바뀌면 HTML을 고쳐야 합니다.
- **로그 300줄 상한** (`:522`) — 3~4시간 세션에서 9명이 굴리면 초반 기록이 잘립니다.
  세션 후 리플레이를 쓰고 싶다면 내보내기 기능이 필요합니다.

## 3. 콘텐츠 공백

### 3-1. 시나리오 「역참-0」이 없다

**심각도: 치명**

룰북 6장이 명시적으로 참조하지만 자료에 없습니다([errata R-6](errata.md#r-6-시나리오-역참-0-문서-부재)).
웹도구에 최종 보스로 보이는 "역참 인격체 코어 '길잡이'"(HP 40 / AC 15)만 하드코딩되어 있습니다.

**규칙과 캐릭터는 이미 돌릴 수 있는 수준인데, "오늘 밤 뭘 플레이하는가"가 통째로 비어 있습니다.**
저장소에서 가장 시급한 결손입니다.

필요한 것: Act별 목표 시간(룰북이 "Act별 목표 소요시간을 참고"하라고 하므로), 씬 목록,
NPC 스탯, 8인이 두 그룹으로 갈리는 분기 지점, 클라이맥스에서 잔향이 얼마나 쌓이도록
설계했는지.

### 3-2. 교환장 구역 설정 ([errata R-1](errata.md#r-1-교환장-구역-정의-누락))

### 3-3. 잔향 획득량 가이드가 얇다

"장면당 GM이 정한 만큼(보통 1d6~2d6)"이 유일한 지침입니다. 3~4시간에 25/50/75
임계치를 몇 번 넘기게 설계했는지가 없으면, GM마다 잔향이 30에서 끝나거나 100을 넘겨
캐릭터가 반쯤 죽은 채 클라이맥스에 들어갑니다. **원샷은 재조정할 다음 세션이 없습니다.**

→ 권장: 시나리오 문서에 "Act 1 종료 시 20~25, Act 2 종료 시 45~55, 클라이맥스 진입 시
70 전후"처럼 목표 곡선을 명시. 여파화(50 이상)를 최소 한 번은 겪게 하는 게 이 규칙을
넣은 이유일 테니, 그 타이밍을 시나리오가 보장해야 합니다.

## 4. 구현 순서

각 단계는 그 자체로 세션에서 쓸 수 있는 상태로 끝납니다. 도중에 멈춰도 손해가 없습니다.

### 0단계 — 저장소 정리

> 이 커밋에서 완료

원본 보존, 문서 마크다운화, 데이터 JSON 분리, 정합성 검사기.
`data/*.json`이 이제 정본이고 문서는 뷰입니다.

### 1단계 — 웹도구 응급처치 (반나절)

기능 추가 없이 "지금 터지는 것"만 막습니다.

1. 스토리지 폴백 (`window.storage` → `localStorage` → 메모리) + 현재 모드 표시 — 2-1
2. 이스케이프 함수 도입 — 2-3
3. 비밀 가리기 (점유자 + GM만) — 2-4

### 2단계 — 규칙 데이터화

> 절반 완료

`data/rules.json`에 DC표·4단계·무기·잔향·여파화·조합·구역을 옮겼습니다.
남은 일은 **웹도구가 하드코딩 대신 이 파일을 읽게 하는 것**입니다.
`PREGENS`/`MONSTERS`/`DC_TABLE` 상수를 `data/*.json` 로딩으로 교체합니다.

> 단일 HTML 파일을 유지하려면 fetch가 `file://`에서 막히므로, 빌드 단계에서
> JSON을 HTML에 인라인하는 방식이 낫습니다. 배포물은 여전히 파일 하나입니다.

### 3단계 — 판정 엔진 (핵심)

1. 주사위 탭 → 판정 탭: 캐릭터/기술 선택 + DC 입력 + 상황 보정
2. 능력치·숙련·잔향·부상 보정 자동 합산
3. 4단계 결과 자동 판정 + 자연 20/1 표시
4. 그룹 판정 화면 (GM이 요청 → 전원 굴림 → 과반 집계 → 조력자 +2)

**여기까지가 "종이보다 나은 도구"의 최소선입니다.**

### 4단계 — 상태 자동화

1. HP 변화 → 부상 단계 자동 갱신 + 판정 보정 반영
2. 잔향 임계치 도달 시 경고 + 페널티 자동 적용
3. 여파화 d10 굴림 버튼 → 결과를 캐릭터에 부착
4. 즉석 조합 UI (결정편 자동 차감)

### 5단계 — 동기화 재설계

2-2의 키 분리. 여기서 백엔드 선택을 정해야 합니다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **아티팩트 유지 + 키 분리** | 추가 인프라 0, 배포는 링크 하나 | 아티팩트가 살아있어야 함, 오프라인 불가 |
| 정적 호스팅 + 실시간 백엔드 | 진짜 실시간(폴링 불필요), 세션 기록 영구 보존 | 계정·키 관리 필요 |
| **GM 단말이 진실의 원천** | 서버 없음. GM 화면이 상태를 갖고 플레이어는 읽기 + 굴림만 | GM이 나가면 세션 정지 |

**당장은 첫 번째를 권합니다.** 키만 쪼개도 실제로 겪는 문제(로그 유실, HP 되돌아감)는
거의 사라지고, 인프라가 늘지 않습니다. 세션 기록을 남기고 싶어질 때 두 번째로 갑니다.

### 6단계 — 콘텐츠

시나리오 「역참-0」 문서화 → 몬스터/NPC를 `data/`로 → 시나리오를 갈아끼울 수 있는 구조로.

## 5. 요약

- **가장 시급한 건 시나리오 문서**입니다. 규칙과 캐릭터는 돌릴 수 있는 수준인데
  플레이할 내용이 없습니다.
- **도구에서 가장 시급한 건 판정 엔진**입니다. 4단계 결과와 그룹 판정 — 이 시스템을
  특별하게 만드는 두 규칙이 도구에 없어서, GM이 8인분을 암산하고 있습니다.
- **기술적으로 가장 시급한 건 스토리지 폴백**입니다. 지금 다운로드한 파일은
  새로고침 한 번에 전부 날아갑니다.
- 경쟁 상태는 락이 아니라 **키 분리**로 푸는 게 이 구조에 맞습니다.
