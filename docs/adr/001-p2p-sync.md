# ADR-001. 세션 동기화를 아티팩트 스토리지에서 P2P로 옮긴다

- 상태: **채택**
- 대체하는 것: [roadmap.md 5단계](../roadmap.md#5단계--동기화-재설계)의 3가지 선택지 비교
- 관련 문제: [roadmap 2-1](../roadmap.md#2-1-아티팩트-밖에서는-저장-자체가-안-된다), [2-2](../roadmap.md#2-2-방-상태-갱신에-경쟁-상태가-있다), [2-4](../roadmap.md#2-4-gm-전용-비밀이-전원에게-보인다)

## 맥락

현재 웹도구는 `window.storage`(Claude 아티팩트 런타임)에 방 상태를 통째로 저장하고
4초마다 폴링합니다. 여기서 세 가지가 동시에 걸립니다.

1. 아티팩트 밖에서는 저장이 아예 안 됨 — 다운로드한 파일은 새로고침 한 번에 초기화
2. 읽기-수정-쓰기 경쟁 — 9명이 쓰면 마지막 쓰기가 이기고 굴림 기록이 사라짐
3. 공유 스토리지에 비밀이 들어있어, 렌더링 단계에서 가리는 것 말고는 방법이 없음

세 번째가 특히 아픕니다. 사전 제작 캐릭터의 비밀은 세션 중반에 터뜨리도록 설계된
장치인데, 데이터가 모두의 브라우저에 이미 도착해 있으면 개발자 도구를 여는 순간 끝입니다.
**"안 보여주기"가 아니라 "안 보내기"가 되어야 합니다.**

## 결정

**GM 단말을 허브로 하는 스타 토폴로지 P2P(WebRTC DataChannel)로 동기화하고,
각 클라이언트의 `localStorage`를 지속 계층으로 둔다.**

```
        플레이어 A ─┐
        플레이어 B ─┤
        플레이어 C ─┼──▶ [ GM 단말 ] ◀── 진실의 원천
        플레이어 D ─┤         │
        ...        ─┘         └─▶ localStorage (세션 저장 파일)
```

- 플레이어는 **의도(intent)** 를 보냅니다: "내 HP를 12로", "은신 판정 14 나옴"
- GM 단말이 받아서 적용하고 **결과를 브로드캐스트**합니다
- 각자 자기 `localStorage`에 마지막 상태를 캐시합니다

### 왜 스타인가 (풀 메시가 아니라)

9명 풀 메시는 36개 연결이고 상태 합의(CRDT 또는 벡터 클록)가 필요합니다.
스타는 **8개 연결**이고 합의가 필요 없습니다 — GM이 순서를 정하는 단일 지점이니까요.

그리고 이건 이미 이 게임의 구조입니다. **TRPG에는 원래 심판이 한 명 있습니다.**
분산 합의 문제를 소프트웨어로 풀 이유가 없습니다. 규칙이 이미 풀어놨습니다.

### 부수 효과로 해결되는 것들

| 기존 문제 | P2P 스타에서 |
|---|---|
| 경쟁 상태 (roadmap 2-2) | GM이 단일 직렬화 지점이라 **경쟁 자체가 없음**. CAS도 락도 불필요 |
| 비밀 노출 (roadmap 2-4) | GM이 점유자에게만 선택 전송 — **세션 중 생기는 정보에 한해** 데이터가 안 감 (아래 단서 참고) |
| 중복 점유 (roadmap 2-5) | GM이 선착순 판정. 두 번째 요청은 거절 응답 |
| 4초 폴링 지연 | DataChannel push — 굴림 결과가 즉시 뜸 |
| 입력 중 동기화 정지 (roadmap 2-6) | 전체 재렌더가 사라지므로 가드 자체가 불필요 |

DataChannel은 DTLS로 종단간 암호화됩니다. 시그널링 서버는 방 코드와 연결 메타데이터만
보고 **게임 데이터는 보지 못합니다.**

### 단서 — 비밀 차단은 아직 절반만 이뤄졌다

이 문서 초판은 "다른 사람의 비밀은 애초에 그 브라우저에 도착하지 않는다"고 썼습니다.
**구현해 보니 사실이 아닙니다.** 명세 03 구현 후 실측한 결과:

| 정보 | 현재 상태 |
|---|---|
| 세션 중 생기는 것 (캐릭터 메모 등) | ✅ GM이 점유자에게만 전송. 남에게 안 감 |
| **사전 제작 캐릭터의 `secret` 16개** | ❌ **빌드 시 모든 클라이언트의 HTML에 인라인됨** |

원인은 P2P가 아니라 **배포 방식**입니다. 이 도구는 "HTML 파일 하나 받아서 열기"로
배포되고, 오프라인 우선 원칙(네트워크 없이도 100% 동작) 때문에 `data/characters.json`
전체가 빌드 산출물에 박힙니다. 개발자 도구를 열면 16개 비밀이 전부 보입니다.

즉 현재 비밀 보호 수준은 **명세 01의 렌더링 차단 그대로**입니다 — "안 보여주기"이지
"안 보내기"가 아닙니다. P2P가 이 문제를 자동으로 풀어줄 거라 본 것이 오판이었습니다.

실제 해법은 빌드를 쪼개는 것입니다 → [명세 04](../specs/04-secret-split.md).
`npm run verify:ui`의 "B의 화면 어디에도 비밀이 없음" 검사가 통과하는 것은
**렌더링 기준**이며, DOM 소스나 콘솔에서는 여전히 읽힙니다. 검사 이름에 속지 마세요.

## 대안 비교

| 방식 | 인프라 | 실시간 | 오프라인 | 위험 |
|---|---|---|---|---|
| 현행 (아티팩트 스토리지) | 없음 | 4초 폴링 | ❌ | 아티팩트 수명에 종속, 경쟁 상태 |
| 실시간 백엔드 (Supabase 등) | 계정·키·요금 | ✅ | ❌ | 원샷 한 번 하자고 인프라를 운영해야 함 |
| **P2P 스타 (채택)** | 시그널링 브로커만 | ✅ | 부분적 | NAT 통과 실패 가능성 |

## 감수하는 대가

정직하게 적습니다. **P2P는 테이블에서 실패할 수 있는 새 지점을 만듭니다.**

1. **시그널링은 여전히 서버가 필요합니다.** WebRTC는 스스로 부트스트랩하지 못합니다.
   공개 브로커(PeerJS 클라우드)를 쓰면 인프라는 0이지만 제3자 의존이 생깁니다.
2. **NAT 통과 실패.** STUN으로 대부분 뚫리지만, 대칭형 NAT이나 빡빡한 회사망에서는
   TURN 릴레이가 필요하고 그건 공짜가 아닙니다. 현실적으로 한두 명은 못 붙을 수 있습니다.
3. **GM이 나가면 세션이 멈춥니다.** 허브가 사라지니까요.
4. **굴림을 클라이언트가 굴립니다.** 마음먹으면 거짓말할 수 있습니다.

### 그래서 지켜야 할 원칙

> **P2P는 동기화 계층이지 저장 계층이 아니다.
> 네트워크가 하나도 안 붙어도 도구는 100% 동작해야 한다.**

3시간짜리 원샷을 시작한 지 5분 만에 NAT 디버깅을 하고 있으면 그날 세션은 망합니다.
따라서 폴백 사다리를 이 순서로 강제합니다.

```
1. 로컬 우선   localStorage가 각 클라이언트의 진실.
              연결 0명이어도 캐릭터시트·주사위·판정이 전부 동작한다.
2. P2P 연결    붙으면 동기화 계층이 얹힌다. 현재 연결 상태를 UI에 항상 표시.
3. 연결 실패   조용히 로컬 모드로 남는다. 오류 팝업으로 세션을 막지 않는다.
4. 최후 수단   GM이 세션 상태를 JSON으로 내보내기/가져오기.
              GM 브라우저가 죽어도 다른 사람이 이어받을 수 있다.
```

4번은 3번의 보험이 아니라 **GM 이탈(대가 3번)의 해법**이기도 합니다.

굴림 신뢰(대가 4번)는 **지인끼리 하는 원샷이므로 문제 삼지 않습니다.**
필요하면 "GM 굴림 모드"(GM이 전원 대신 굴림) 토글 하나로 충분하고,
커밋-리빌 같은 건 이 규모에 과합니다.

## 구현 메모

- **라이브러리**: PeerJS. 방 코드를 그대로 피어 ID로 쓸 수 있어서
  **기존 "방 코드 입력" UX가 한 글자도 바뀌지 않습니다.**
  GM은 `new Peer('hapgyeong-ABCD')`, 플레이어는 `peer.connect('hapgyeong-ABCD')`.
- **CDN 대신 벤더링**: `web/vendor/peerjs.min.js`를 저장소에 넣고 빌드 시 인라인.
  배포물은 여전히 HTML 파일 하나입니다.
- **네임스페이스**: 공개 브로커는 전역 ID 공간이므로 `hapgyeong-` 접두사 필수.
  4자 코드는 충돌 가능성이 있으니 충돌 시 재생성 유도.

상세 구현은 [`specs/03-p2p-sync.md`](../specs/03-p2p-sync.md).
